Compare kern/mpentry.S side by side with boot/boot.S. Bearing in mind that kern/mpentry.S is compiled and linked to run above KERNBASE just like everything else in the kernel, what is the purpose of macro MPBOOTPHYS? Why is it necessary in kern/mpentry.S but not in boot/boot.S? In other words, what could go wrong if it were omitted in kern/mpentry.S? Hint: recall the differences between the link address and the load address that we have discussed in Lab 1.
    The MPBOOTPHYS macro calculates the physical load address of symbols in mpentry.S. 
    Because mpentry.S is linked with the rest of the kernel, its symbols are assigned high 
    virtual link addresses above KERNBASE.MPBOOTPHYS manually translates these virtual link
    addresses into their actual physical load addresses so the CPU can correctly fetch the 
    data. This isn't needed in boot/boot.S because the bootloader's link address perfectly 
    matches its load address (0x7C00). If MPBOOTPHYS were omitted in mpentry.S, the AP would 
    attempt to use high virtual addresses while still in real mode, causing an invalid memory
    access and an immediate crash before reaching protected mode.

It seems that using the big kernel lock guarantees that only one CPU can run the kernel code at a time. Why do we still need separate kernel stacks for each CPU? Describe a scenario in which using a shared kernel stack will go wrong, even with the protection of the big kernel lock.
    Even though the Big Kernel Lock (BKL) ensures that only one CPU can actively execute kernel 
    software at a time, separate kernel stacks are still strictly necessary because the initial 
    transition from user mode to kernel mode is a hardware-driven event that occurs before any 
    software lock can be acquired. If multiple CPUs shared a single kernel stack, a simultaneous 
    trap such as two CPUs receiving a timer interrupt at the exact same microsecond, would cause 
    the hardware to blindly push this state to the exact same memory addresses at the same time, 
    eventually causing a crash. 

In your implementation of env_run() you should have called lcr3(). Before and after the call to lcr3(), your code makes references (at least it should) to the variable e, the argument to env_run. Upon loading the %cr3 register, the addressing context used by the MMU is instantly changed. But a virtual address (namely e) has meaning relative to a given address context–the address context specifies the physical address to which the virtual address maps. Why can the pointer e be dereferenced both before and after the addressing switch?
    The pointer e is a virtual address that resides in the kernel's portion of memory. In the JOS 
    memory layout, every single page directory in the system contains the exact same virtual to 
    physical memory mappings for all addresses above UTOP. Therefore, when lcr3() loads the %cr3 
    register with the new environment's page directory, it swaps the addressing context for the 
    user memory (below UTOP), but the mappings for the kernel memory remain the same. Because both 
    the old and new page directories map the virtual address of e to the exact same physical memory 
    location, the pointer can be dereferenced both before and after the context switch.

Whenever the kernel switches from one environment to another, it must ensure the old environment’s registers are saved so they can be restored properly later. Why? Where does this happen?
    While the Big Kernel Lock (BKL) restricts kernel code execution to a single CPU at a time, it 
    cannot protect the hardware-level context switch that happens the exact moment a trap occurs.
    Before the kernel software has a chance to request the BKL, the x86 processor automatically 
    pushes critical state onto the kernel stack. If all CPUs shared the same stack, two processors 
    taking an interrupt simultaneously would push their state to the exact same memory addresses. 
    This collision would completely corrupt the trap frames before the software lock is ever engaged, 
    resulting in a fatal crash when the system eventually tries to restore that corrupted state to 
    return to user mode.
